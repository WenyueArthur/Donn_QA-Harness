# qa-flow 产品使用说明书

版本：qa-flow 0.1.0　｜　更新日期：2026-11-16

本说明书中的命令与屏幕输出均已在本机实测（macOS arm64，Python 3.13.7）。
实测只证明命令可以执行，不代表任何验收场景已通过。

---

## 1. 产品是什么

qa-flow 是一个命令行工具，用来按固定流程推进一个需求的完整测试工作。
它把一个需求从「需求质检」一直推进到「复盘与知识回流」，共 12 个阶段。

它的核心特点：

- AI 只负责起草内容（质检报告、测试分析、用例等）。
- 阶段能否推进，由系统根据校验结果、真实执行回执和人的确认来判定。
- 所有结论都留有证据，修改后旧结论自动标记为过期（Stale，即依赖的输入已变化）。
- 数据全部保存在本机：一个 SQLite 数据库加一个证据目录，不依赖网络。

### 1.1 适合做什么

- 用合成数据完整体验一次 QA 全流程（离线实验，无需账号）。
- 登记飞书项目工作项及其挂载的飞书文档作为需求来源（由已配置飞书 MCP 的 Agent 读取）。
- 在真实项目中，配合 Claude Code 完成需求质检、测试分析、测试计划、用例设计和用例质检。
- 记录业务确认、跟踪阶段状态、导出交付报告（Markdown / HTML / JSON）。

### 1.2 当前不能做什么

以下能力尚未接入，相关阶段在真实项目中会显示「受阻」：

- 在飞书项目中创建或修改缺陷（只有实验平台桩）。
- 直接连接飞书读取需求（由 Agent 读取后交给 qa-flow，qa-flow 不能证明内容与飞书原文一致）。
- 调用真实大模型（只有实验模型桩，真实项目需由 Claude Code 生成内容后提交）。
- 原生审批身份核验（本地答复不是已认证签字）。
- 生产只读连接器（「上线验证」阶段始终显示待定）。

## 2. 先理解五个概念

| 概念 | 含义 |
|---|---|
| 需求（任务） | 一次 `start` 创建一个任务，对应一份或多份需求文档。 |
| 工作区 | 保存数据的目录，默认为当前目录下的 `.qa-workspaces/`。 |
| 阶段 | 流程的 12 个步骤，见附录 A。每个阶段有状态和判定。 |
| 待确认 | 需要人做决定的问题，编号为 Q1、Q2……，用 `review` 处理。 |
| 合成实验 | `demo` 使用的虚构需求和数据，结果不代表真实业务。 |

**工作区位置规则**：系统从当前目录开始向上查找 `.qa-workspaces/` 目录。
找不到时，在当前目录新建。因此请始终在同一个目录下执行命令。
也可以设置环境变量 `QA_FLOW_HOME`，或在命令中加 `--workspace <目录>` 指定位置。

**两种答复的区别**：

- 你自己答复的问题，记录为 `local_attested`，表示「本机操作者记录」。
- 实验审批桩给出的答复，记录为 `simulated`，表示「模拟答复」。
- 两者都不是已认证的产品负责人签字。

## 4. 第一次使用：离线实验

离线实验用一个虚构的「退款」需求走完全流程。
它不需要账号、网络或任何配置，适合先熟悉操作。

### 4.1 操作步骤

1. 新建一个空目录作为实验目录，并进入该目录。

```bash
mkdir -p ~/qa-demo && cd ~/qa-demo
```

2. 启动实验。系统会自动完成需求质检和技术方案质检，然后停在第一个业务问题。

```bash
python -m qa_flow demo
```

3. 查看待确认问题。屏幕会逐项显示问题、原文依据、影响范围和选项。
   在终端中可以直接输入选项字母答复；输入 `t` 转交责任人，输入 `s` 暂不处理。

```bash
python -m qa_flow review
```

4. 也可以用一条命令答复和转交（问题编号以屏幕为准）。需要他人决定的问题只能用 `--transfer` 转交。

```bash
python -m qa_flow review --answer Q1=A --transfer Q2=product --transfer Q3=product
```

5. 继续推进。系统会生成测试分析、测试计划、用例设计并完成用例质检。

```bash
python -m qa_flow resume
```

6. 重复「`review` 查看 → `review --answer` 答复 → `resume` 继续」，直到屏幕不再提示待确认事项。
7. 导出交付报告。

```bash
python -m qa_flow export --output ./交付
```

### 4.2 实测中会遇到的问题

下表是一次实测的完整顺序，供你对照。

| 编号 | 问题 | 处理方式 |
|---|---|---|
| Q1 | 以什么字段判定「同一回调」？ | 自己答复，例如 `--answer Q1=A` |
| Q2、Q3 | 部分退款后的订单状态、到账通知由谁发送 | 产品负责人决定，用 `--transfer` 转交 |
| Q4 | 是否批准测试计划？ | 自己答复，`--answer Q4=A` |
| Q5–Q9 | 用例 C1–C5 的关键业务预期是否正确 | 转交产品负责人，实验审批桩会给出模拟答复 |
| Q10 | 是否确认测试准出？ | 自己答复，`--answer Q10=A` |
| Q11 | 是否把经验条目写入知识库？ | 自己答复，`--answer Q11=A` |

实验中会自动发生以下事件：

1. 在带缺陷的构建 build1 上执行 7 条用例，C1、C3 失败。
2. 在实验平台桩上创建 2 个缺陷，并上传、回读核对附件。
3. 部署修复构建 build2，复测与相邻回归全部通过。
4. 按授权关闭 2 个缺陷，等待你确认准出。

### 4.3 实验结束时的正常状态

最终屏幕会显示：「测试已准出；上线验证待实际部署后核验」。

- Q2、Q3 仍显示「需他人决定」，这是预期行为：转交不等于答复。
- 「上线验证」显示待定，因为没有生产只读连接器，这不是失败。

### 4.4 清理实验数据

实验数据保存在 `~/qa-demo/.qa-workspaces/lab-demo/`，系统不会自动删除。
确认不再需要后，删除整个实验目录即可。

## 5. 在真实项目中使用

真实项目分两部分工作：

- 管理员：为项目准备一次配置。
- 测试人员：每个需求重复「开始 → 生成内容 → 确认 → 继续 → 导出」。

### 5.1 管理员：建立项目工作区（每个项目一次）

1. 新建一个项目工作目录，并在其中建立 `config/` 和 `sources/` 两个子目录。

```bash
mkdir -p ~/qa-work/config ~/qa-work/sources && cd ~/qa-work
```

2. 复制旧规则冻结清单到配置目录。真实项目必须使用旧规则桥接（`legacy_bridge`）。

```bash
cp /Users/donnie/PycharmProjects/qa-harness/docs/baseline/legacy-rule-manifest.json ~/qa-work/config/
```

3. 编写配置文件 `~/qa-work/config/my-project.json`。模板见附录 C，需要修改：
   - `project.id` 与 `project.name`：项目编号与业务名称。
   - `workspace.source_read_roots`：允许读取需求文档的目录，填写绝对路径。
4. 预览配置。返回 `"problems": []` 表示校验通过，此时尚未写入。

```bash
python -m qa_flow admin setup --config config/my-project.json --name my-project
```

5. 应用配置，生成项目工作区 `.qa-workspaces/my-project/`。

```bash
python -m qa_flow admin setup --config config/my-project.json --name my-project --apply
```

6. 检查运行环境与能力边界。

```bash
python -m qa_flow admin doctor
```

**配置注意事项**：

- 配置中禁止出现密码、Token、API Key 等明文，校验会直接拒绝。需要凭证时写 `credential_ref`（凭证引用名）。
- 冻结清单会逐个核对旧仓库 `qa-skills/qa-mainflow/` 的文件摘要。旧仓库文件有任何变化，规则即判定为不可用。
- 修改规则或准出标准只能通过 `admin setup` 重新应用。直接改配置文件会被识别为未授权改动。

### 5.2 安装 qa-flow Skill（每台电脑一次）

真实项目中，质检报告、测试分析、用例等内容由 Claude Code 生成。
Claude Code 需要先加载 qa-flow Skill，才知道如何调用命令行并提交内容。
当前该 Skill 尚未安装到 `~/.claude/skills/`，请执行：

```bash
ln -s /Users/donnie/PycharmProjects/qa-harness/skills/qa-flow ~/.claude/skills/qa-flow
```

安装后，在 Claude Code 中说「用 qa-flow 继续这个需求」即可触发。

### 5.3 测试人员：处理一个飞书需求

业务需求通常是飞书项目工作项，以及工作项中挂载的飞书文档（产品文档、技术方案等）。
qa-flow 不直接连接飞书。读取工作由已配置飞书项目 MCP 的 Agent 完成（Claude Code、Cursor、Codex 均可）。
这样避免在 qa-flow 中重复实现飞书连接，也不需要为 qa-flow 单独配置飞书令牌。

分工如下：

| 谁 | 做什么 |
|---|---|
| Agent | 读取工作项字段、评论和挂载文档，把工具原始输出保存为文件，写成来源包（`bundle.json`） |
| qa-flow | 把工作项渲染成文本，找出所有挂载文档链接，检查是否漏读，登记来源并跟踪新鲜度 |

操作步骤：

1. 在项目工作目录下打开 Claude Code，发送飞书项目工作项链接，例如：

```text
用 qa-flow 开始这个需求：https://project.feishu.cn/wk-dm/story/detail/7075114327
```

2. Agent 按 qa-flow Skill 读取工作项、评论和挂载文档，生成来源包并执行预检。
   预检未通过时，Agent 会补读漏掉的文档，或如实登记读取失败的原因。
3. 预检通过后，Agent 执行以下命令登记来源并开始需求（也可以自己执行）：

```bash
python -m qa_flow start --bundle "./飞书来源/7075114327/bundle.json"
```

4. 核对屏幕上的「已登记飞书来源」列表，确认每份文档的用途和读取状态。实测输出如下：

```text
已登记飞书来源（Agent 读取，qa-flow 未直接连接飞书）：
  - 飞书项目工作项《1【花果支持下订阅订单】支持流失用户再激活需要再次续订》（工作项本身；已读取）
  - 需求文档《花果支持退订学员再次订阅发单 PRD》（字段「产品文档」；已读取）
```

5. 在 Claude Code 中请它按 qa-flow Skill 生成并提交当前阶段的内容，例如「为这个需求做需求质检并提交」。
6. 处理系统提出的业务问题。

```bash
python -m qa_flow review
```

7. 继续推进到下一阶段。

```bash
python -m qa_flow resume
```

8. 重复第 5–7 步，直到当前能推进的阶段全部完成。
9. 导出交付报告。

```bash
python -m qa_flow export --output "./交付"
```

**开始前请核对**：屏幕第一行的需求名称、来源和环境（真实项目显示 `test`）。

### 5.4 飞书需求更新后

飞书来源默认 72 小时后过期（配置项 `timing.source_max_age_hours`）。过期后不再形成新结论。

- `status` 或 `resume` 提示「飞书来源已超过新鲜度期限」时，请 Agent 重新读取同一工作项，再执行 `start --bundle`。
- 同一工作项再次登记会继续使用原任务，不会新建。
- 只有内容变化的文档生成新版本，依赖旧内容的结论和确认自动过期，只需重新确认受影响的部分。
- 工作项新增或移除了挂载文档时，来源列表同步更新，相关结论重新核验。

### 5.5 来源包被拒绝时

`start --bundle` 发现以下情况会拒绝登记（退出码 4），工作区不写入任何内容：

| 屏幕提示 | 原因 | 处理方式 |
|---|---|---|
| 未读取工作项中挂载的文档 | 字段或评论里有文档链接，来源包中没有 | 请 Agent 读取该文档，或登记读取失败原因 |
| 字段还有下一页 / 评论只保存了部分页 | 工具输出分页未读完 | 请 Agent 读完全部分页 |
| 工作项 ID 不一致 | 链接与保存的内容不是同一个工作项 | 请 Agent 重新读取 |
| 读取失败时必须写明原因 | 文档标记为读取受阻，但没写原因 | 补充真实原因，如「无访问权限」 |
| 读取时间晚于当前时间 | 读取时间填写错误 | 填写实际读取时间 |

直接把飞书链接传给 `start --source` 会被拒绝（退出码 3），并提示改用来源包。

### 5.6 本地文件需求

需求是本地 Markdown 文件时，放入配置允许读取的目录后执行：

```bash
python -m qa_flow start --source "./sources/积分兑换.md"
```

需求文档无法识别标题时，加 `--title "业务名称"` 指定。

## 6. 日常命令速查

| 想做什么 | 命令 |
|---|---|
| 开始一个飞书需求 | `python -m qa_flow start --bundle "./飞书来源/<工作项 ID>/bundle.json"` |
| 预检来源包（不写入） | `python -m qa_flow api source inspect --bundle "<来源包>"` |
| 开始一个本地文件需求 | `python -m qa_flow start --source "./需求.md"` |
| 继续未完成工作 | `python -m qa_flow resume` |
| 查看待确认问题 | `python -m qa_flow review` |
| 答复问题 | `python -m qa_flow review --answer Q1=A --note "Q1=答复理由"` |
| 转交问题 | `python -m qa_flow review --transfer Q2=product` |
| 查看进度 | `python -m qa_flow status` |
| 查看各阶段详情 | `python -m qa_flow status --details` |
| 导出报告 | `python -m qa_flow export --output "./交付"` |

所有日常命令都支持以下选项：

| 选项 | 作用 |
|---|---|
| `--task "业务名称"` | 存在多个需求时，按名称选择要操作的需求 |
| `--details` | 显示各阶段判定、证据编号、测试结果和缺陷 |
| `--json` | 输出机器可读的 JSON 回执 |
| `--non-interactive` | 不在终端等待输入，缺少选择时立即返回 |
| `--workspace <目录>` | 指定工作区位置 |

`--transfer` 可用的角色：`product`（产品负责人）、`developer`（研发负责人）、`admin`（管理员）。

## 7. 读懂屏幕输出

每条命令执行后，屏幕按固定格式显示当前状态。以下是一次实测输出：

```text
需求：退款实验（合成数据）
来源：refund-requirement.md、refund-tech.md、refund-selftest.md    环境：lab（合成实验）
当前：需求测试分析：受阻。
原因：业务问题尚未有效答复：Q1 同一回调只记账一次，以什么字段判定“同一回调”？。
已有：需求质检、技术方案质检 有效。
需他人决定：部分退款后订单状态应显示什么？（产品负责人）；……
下一步：逐项处理你负责的业务确认；使用 “review”（范围：1 项；只记录本地答复，不是外部认证签字）。
同步：worker 未运行，自动刷新与提醒未启用。
本次：只操作本机实验资源与实验平台桩；未写入真实平台，未发布系统。
```

| 行 | 怎么看 |
|---|---|
| 当前 | 流程卡在哪个阶段，以及该阶段状态 |
| 原因 | 为什么停在这里 |
| 已有 | 已经完成且仍有效的阶段 |
| 需他人决定 | 你无权答复、需要转交的问题 |
| 下一步 | 系统建议执行的命令及其影响范围 |
| 本次 | 这条命令实际做了什么、没做什么 |

阶段状态的含义：

| 状态 | 含义 |
|---|---|
| 已完成 | 阶段产物有效且判定通过 |
| 待处理 | 可以开始，但还缺产物 |
| 受阻 | 等待上游阶段、业务答复或批准 |
| 未通过 | 规则计算不通过 |
| 不可判定 | 证据不足，不能下结论（不等于通过或失败） |

## 8. 常见情况与处理

### 8.1 按退出码判断结果

退出码 0 只表示命令执行成功，不表示业务通过。业务结论以屏幕「当前」行为准。

| 退出码 | 含义 | 处理方式 |
|---|---|---|
| 0 | 命令成功 | 查看「当前」与「下一步」 |
| 2 | 参数或内容格式错误 | 按提示修正参数 |
| 3 | 需要选择、确认或授权 | 执行 `review`，或用 `--task` 选择需求 |
| 4 | 证据或产物无效 | 按提示重新生成并提交内容 |
| 5 | 外部操作结果未知 | 执行 `resume`，系统会先查询核对，不会重复提交 |
| 6 | 依赖或文件读写不可用 | 检查配置、文件路径，或请管理员执行 `admin doctor` |
| 7 | 内部一致性错误 | 停止操作，联系管理员 |

### 8.2 具体场景

| 场景 | 处理方式 |
|---|---|
| 存在多个需求，命令提示「需要选择」 | 加 `--task "业务名称"` |
| 存在多个项目，`start` 提示选择项目 | 加 `--project "项目名称"` |
| 终端被关闭或命令被中断 | 已提交的工作会保留，执行 `resume` 继续 |
| 需求文档修改了 | 执行 `resume`，系统会刷新来源，依赖旧版本的结论自动过期 |
| 屏幕提示「来源中含诱导性文字」 | 无需处理，系统已把这些文字当作普通资料 |
| 同一份文档再次执行 `start` | 系统会继续使用原任务，不会重复创建 |
| 提示「数据库正被其他操作占用」 | 稍后重试，本次未写入 |

**请不要做以下操作**：手工修改 `.qa-workspaces/` 下的 JSON 或数据库、关闭校验、代替他人答复。
这些操作会被系统识别为未授权改动，或导致结论失效。

## 9. 管理员维护

### 9.1 备份与恢复

1. 创建备份。备份完成后会自动核验，返回 `"ok": true`。

```bash
python -m qa_flow api backup create --output ./备份
```

2. 需要时单独核验备份。

```bash
python -m qa_flow api backup verify --path ./备份
```

3. 恢复到一个新目录（不要覆盖原工作区）。

```bash
python -m qa_flow api backup restore --from ./备份 --to ./恢复
```

### 9.2 定时同步

worker 负责刷新过期来源、同步缺陷状态、登记提醒。它不会常驻运行，需要手动或定时执行：

```bash
python -m qa_flow api worker tick --once
```

未执行时，屏幕会显示「worker 未运行，自动刷新与提醒未启用」。
飞书来源过期时，worker 不会自行重读，只在结果的 `agent_fetch_required` 中列出需要 Agent 重新读取的来源。

### 9.3 运行自动化测试

在项目目录执行，终端会显示实时进度条：

```bash
scripts/run-tests.sh
```

只运行部分用例时，参数原样传给 pytest，例如 `scripts/run-tests.sh tests/acceptance -k ac108`。

### 9.4 其他管理命令

| 命令 | 作用 |
|---|---|
| `admin doctor` | 报告版本、各项能力与边界 |
| `admin legacy-freeze` | 重新冻结旧规则仓库的文件摘要 |
| `admin parity-record` / `parity-check` | 录制并对照旧规则输出基线 |
| `admin expire-evidence` | 按保留策略销毁私有证据 |
| `api --help` | 查看全部机器接口（开发与排障用） |

## 10. 安全边界

系统遵守以下规则，任何命令都无法绕过：

- AI 只提出内容，阶段状态由系统根据校验和确认推进。
- 未知、未执行、过期、受阻和失败分别记录，不会合并成「通过」。
- 已登记的内容不可修改，修订会生成新版本，依赖它的结论自动过期。
- 外部操作先登记再执行，结果未知时先查询核对，不会盲目重发。
- 导出只写本地文件，不会写入飞书、修改缺陷或发布系统。
- 数据不完整时指标显示为空，不会补 0。
