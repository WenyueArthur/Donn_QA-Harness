# QA 全流程重构测试与验收方案

状态：可以据此实现测试，尚未测试未来的新系统。日期：2026-11-15。
配套：[重构设计](01-rebuild-design.md)、[一页上手指南](QUICKSTART.md)、[需求清单](requirements.json)、[场景细则](acceptance-cases.json)、[夹具](lab-fixtures.json)。

## 1. 测试目标与结果边界

测试目标是证明已定义的行为成立，并证明错误证据不会产生错误通过。
优先检验失败、未知、过期和恢复路径，再验证成功路径。

本包定义 144 个验收场景，覆盖 60 项需求。
其中包含 8 项易用性要求，已有可靠性场景全部保留。
数量是设计清单，不是已经通过的测试数量。
每个场景包含前置、操作、可判定预期和证据要求。
独立测试代码应按这些规格实现，不能仅检查文档存在。

三种证据不得混用：

| 结果 | 证明范围 | 不能证明 |
|---|---|---|
| 文档与夹具检查通过 | 编号、对应关系、引用和合成数学期望自洽 | 新系统实现正确 |
| 离线与受控实验验收通过 | 核心状态、实际本地执行、异常恢复可工作 | 平台凭证、真实字段、真实审批或生产可用 |
| 真实接入验收通过 | 所指定环境、平台、模型及部署范围内的行为 | 未测业务、其他平台和无限输入也正确 |

不以“通过了 N 条测试”证明需求语义没有遗漏。
完整验收还需要独立原文审阅和真实接入记录。

## 2. 被测对象与测试分层

日常验收使用 `start/resume/review/status/export` 和 `demo`。
机器契约与故障注入使用受控 `api` 入口。
两者必须调用同一应用服务，易用性入口不得绕过原有校验。
验收器不调用内部状态修改函数，不手改数据库来制造正常完成状态。
破坏和故障测试可以在隔离副本中改输入、证据或注入故障。

| 层 | 重点 | 是否需要真实外部凭证 |
|---|---|---|
| `offline` | 契约、规则、证据、决定、计划、指标、跨对象关系 | 否 |
| `lab` | 本地真实请求、脚本运行、平台桩、异常流转与恢复 | 否 |
| `parity` | 旧规则等价、历史只读、测试能抓住人为破坏 | 否，需冻结旧规则源码与样本 |
| `package` | 干净环境、路径、安装和系统能力 | 否 |
| `model` | 选定真实模型的有限样本语义与隐私核验 | 需要该模型合法使用权限 |
| `external` | 真实专用测试空间、原生审批、生产只读取证 | 是，按目标和操作分别授权 |
| `usability` | 未参与开发者独立执行任务、理解确认与错误、恢复和交付 | 不需要；使用已安装的隔离合成实验 |

本次场景分层数量：external 4 项；lab 51 项；model 1 项；offline 79 项；package 2 项；parity 3 项；usability 4 项。
同一场景在多个 OS 或故障点参数化，实际测试实例数可增加。

## 3. 测试环境与隔离

### 3.1 工作区

每个场景建立独立临时目录，不共用 SQLite 文件和数据集。
目录内含数据库、私有原始证据、脱敏证据、派生报告及平台桩账本。
测试不得加载开发者 HOME 中的测试账号、Skill 镜像或生产凭证。
清理只删除该次创建且位于临时根目录内的对象。

来源文件、旧历史文件和受保护文档在运行前后计算摘要。
中文、空格、符号链接、路径越界、不同工作目录均纳入测试。
执行器若不支持网络或进程隔离，应明确拒绝相应能力测试，而不是降级后标通过。

### 3.2 可控条件

- 使用可注入时钟检验过期、提醒、窗口和时区。
- 使用固定随机种子与独立数据重置。
- 使用进程屏障验证竞态，不靠固定 sleep 猜测先后。
- 使用记录型模型桩观察实际发送内容。
- 使用记录型平台桩统计创建、更新、关联和查询次数。
- 使用独立读取连接检查数据库关系和事件完整性。
- 使用受控故障点注入崩溃、断连、部分成功与磁盘写失败。

故障注入接口仅在测试进程显式启用，正式运行默认不可用。
环境变量中不得保存可被业务脚本继承的生产密钥。

## 4. 合成退款实验

实验业务仅用于验证框架，不是现有公司的退款规则。
事实、接口、金额和缺陷均来自合成夹具。

### 4.1 初始状态

| 订单 | 已支付，分 | 已退款，分 | 状态 |
|---|---:|---:|---|
| O100 | 10,000 | 0 | paid |
| O200 | 10,000 | 10,000 | refunded |

金额使用整数分，不用浮点金额。
退款操作者可写，只读角色不可写。

### 4.2 必须由独立业务参考规则判断的行为

1. 检查金额为整数且大于 0，不超过剩余可退额。
2. 检查同幂等键、同载荷返回同一退款。
3. 检查同键不同载荷返回冲突且金额不变。
4. 检查余额更新与退款记录同时成功或同时失败。
5. 检查重复回调只记账一次。
6. 检查并发请求不会使总退款超过已支付金额。
7. 检查只读角色被拒绝且没有副作用。

独立 oracle 可以是简短的纯 Python 参考模型和固定期望表。
不得导入被测退款服务实现或新系统的指标计算函数计算预期。
平台桩的调用账本、退款表和运行结果须互相核对。

### 4.3 确定的顺序期望

| 请求 | 预期状态 | O100 已退款，分 |
|---|---:|---:|
| K1，退款 3,000 | 201 | 3,000 |
| K1，再次退款 3,000 | 200，退款 ID 相同 | 3,000 |
| K1，改为退款 4,000 | 409 | 3,000 |
| K2，退款 8,000 | 400 | 3,000 |
| K3，退款 0 | 400 | 3,000 |

独立并发实验从 O100 已退款 0 重新开始。
两个不同幂等键各退款 7,000，只允许一个成功。
期望总已退款为 7,000，退款记录为 1 条。

### 4.4 三个实验构建

- `buggy_duplicate`：重复请求错误地再次扣减可退余额。
- `fixed`：满足全部合成规则。
- `buggy_neighbor`：重复问题已修复，但错误允许只读角色退款。

三个构建用于证明框架能发现问题、验证修复并捕捉相邻回归。
测试不能只在 fixed 构建上验证全通过。

## 5. 夹具工厂的交付要求

新项目必须实现 `tests/fixtures/build_lab.py`，而非要求人工准备散乱数据。
输入为 `lab-fixtures.json` 和临时根目录。

工厂应输出以下资源和启动回执：

| 资源 | 内容 | 独立检查 |
|---|---|---|
| 来源集合 | 明确规则、缺失信息、矛盾和诱导各类合成原文 | 固定参考事实和摘要 |
| 实验业务服务 | 上述三个退款构建、独立数据库和测试探针 | 直接查询业务结果，不用框架的 pass 字段作预期 |
| 平台桩 | 原生状态、审批、附件、文档及异常模式 | 请求计数、目标 ID、事件修订与最终对象 |
| 模型桩 | 有效、伪造引文、漏项、非法 JSON、注入输出 | 实际接收的脱敏输入与固定响应 |
| 审批桩 | 模拟身份、撤销、到期与对象摘要 | 只能产生 simulated，不能升级 external_verified |
| 数据集 | 每个场景独立的初始数据、重置和清理 | 初态与清理后状态一致 |
| 时钟与屏障 | 手动推进时间和控制竞态 | 不依赖真实等待达到过期 |
| 原规则样本 | 正确、错误、临界、已受阻、过期、引用错误 | 预先审定旧校验输出，而非由新校验器动态生成 |

服务绑定本机环回地址和动态端口。
实际端口通过配置回执传给 CLI，不把固定端口当测试成立条件。
全部测试记录标记 synthetic 或 local_lab。

不能通过调用产品的“自测全部通过”命令来完成独立验收。

对每个拒绝路径，至少检查：

1. 检查稳定错误代码、对象与字段位置。
2. 检查未产生完成事件或越界动作。
3. 检查原文件、旧快照、批准对象和无关需求未改变。
4. 检查必要审计存在且无敏感原值。
5. 检查重新修正输入后可以继续，不出现永久误锁。

## 7. 指标的独立参考值

### 7.1 采纳和修改

原始 AI 集合为 A1、A2、A3、A4。
A1 原样采纳；A2 人工语义修改后采纳；A3 拒绝；A4 人工拆成两条后明确采纳。
另有纯人工新增 M1，不进入 AI 原始集合。

- 采纳率为 3/4，即 0.75。
- 人工修改率为 2/4，即 0.5。
- A4 拆为两条不扩大原始分母。
- 原始决定有 pending 时，输出 incomplete 和 null。
- 无原始 AI 用例时，输出 not_applicable 和 null。

### 7.2 缺陷

B1、B2、B3 为有效唯一缺陷，只有 B3 在线上发现。
B4 是 B3 的重复单，B5 无效。B3 有已确认漏测归因。

- 线上缺陷占比的分子为 1，分母为 3。
- 展示百分比保留两位小数时为 33.33%。
- 已确认漏测数为 1，未确认归因另列。
- 缺少范围、发现窗口或有效性时，不计算确定比例。

参考值不由产品的聚合函数生成。
比较时优先比整数分子分母，再检查显示舍入。

### 7.3 时间

提测接收为 2026-11-16 01:00 UTC。
准出决定为 2026-11-17 05:00 UTC。
暂停区间为 16 日 02:00–06:00 与 05:00–08:00 UTC。

- 日历跨度为 28 小时。
- 暂停并集为 6 小时，不能重复扣除重叠部分。
- 有效经过时间为 22 小时。
- 两个人实际投入共 6 人时。
- 夹具规定每日 8 小时，因此为 0.75 人天。

这些是合成数学期望，不是性能或效率实测。

## 8. 故障、竞态与恢复矩阵

| 注入点 | 检查结果 |
|---|---|
| 证据临时文件完成前退出 | 无有效数据库引用，残留可识别 |
| 证据落盘后、事务前退出 | 最多有孤立证据，不出现已完成对象 |
| 事务写事件后、提交前退出 | 重启后事务回滚，状态与事件一致 |
| 提交成功后、回执前退出 | 同 command_id 重放返回原提交结果 |
| 两个进程提交相同预期修订 | 仅一个成功，另一个明确冲突 |
| 远端已创建、响应丢失 | action=unknown；先查询核对，不重新创建 |
| 附件已上传、关联失败 | 缺陷 ID 保留，只处理关联，不重复建单 |
| 旧 worker 在租约过期后返回 | 不覆盖新修订，结果进入核对 |
| 授权后源变化、发送前 | 重新核验阻断发送，外部调用为 0 |
| 重复或乱序平台事件 | 去重或回读当前状态，不回退状态 |
| 文档被人修改 | 内容冲突停止，不保存成功快照 |
| 进程树超时 | 支持的隔离环境中无遗留子进程，不能误记通过 |
| 磁盘写失败、证据缺失、数据库损坏 | 明确错误，停止推进；恢复不覆盖正常工作区 |
| 时钟跨日、时区变化、重复暂停 | 以 UTC 和区间运算给出相同业务结果 |
| worker 停止与重复 tick | 停止后标新鲜度不足；恢复后同截止点只生成一个提醒动作 |

进程终止测试不证明物理断电安全。
目标机器若要求断电恢复，应使用独立测试设备或虚拟机故障演练，记录 OS、文件系统、运行时和实际结果。

## 9. 有限样本语义和真实接入

### 9.1 真实模型

准备 12 份人工标注的合成材料：明确、缺失、冲突、诱导各 3 份。
先冻结参考事实、应保留的未知、来源位置和不得执行的指令。

1. 记录模型标识、参数、提示词和输入摘要。
2. 逐份调用选定模型，不把失败样本换掉。
3. 检查输出结构、引文和语义。
4. 由独立审阅者对照参考标注，记录每处遗漏与伪造事实。
5. 输出样本级结果与限制，不声称无限输入下准确率为 100%。

通过条件：这 12 份材料没有无依据的已证实断言；必须保留的未知与冲突未被消除；提示注入未触发权限或状态变更。
若某个样本失败，保留失败并修正规则或提示词后重测整个冻结集合。
旧结果和新结果均保留，不只保存最好的一次。

### 9.2 测试平台与审批

使用明确获准的专用空间、测试账号和测试数据。
探测真实字段、状态、附件及审批身份。
验证一次创建、附件回读、已修复、复测、关闭和异常处置。
平台不支持幂等或查询时，验证 unknown 会停止，而不是要求适配器保证不可能的自动恢复。

### 9.3 生产只读与回滚演练

生产只读验收需要真实部署、批准时间窗、目标版本和观测方法。
不能用合成 production 字段代替真实来源。
回滚演练在隔离测试或预生产进行，并核对代码、数据和配置恢复。
生产回滚执行明确不属于本方案的自动化验收范围。

缺少权限或目标时记 blocked，列出受影响用例。
不得把 blocked 改为 skip 后宣布完整接入通过。

## 10. 执行步骤与命令

### 10.1 当前即可执行：检查交付包

在本交付目录执行：

```bash
python3 check_handoff.py
python3 check_handoff.py --negative-selfcheck
```

只检查文档、编号、对应关系、示例期望、新人任务规格和文件清单。
不会连接任何环境，也不会测试尚未实现的新系统。

### 10.2 新项目实施后执行：独立验收

以下命令是目标项目必须支持的测试组织方式。
文件和接口需要按本方案实现后才可执行。

```bash
python3 -m venv .venv
# 激活虚拟环境后，在新项目根执行以下命令
python -m pip install -r dependency-lock.txt
python -m pip install --no-deps -e .
python -m pytest -q tests/unit tests/contracts
python -m pytest -q tests/acceptance tests/fault_injection tests/parity
python -m pytest -q tests/integration --junitxml=artifacts/integration.xml
```

`tests/integration` 默认禁用真实网络。
显式配置批准目标、凭证引用和连接器后才启用对应接入测试。
未配置时报告 blocked，不把它当成功；自动 CI 可只声明离线范围通过。
测试凭证由安全存储注入，不写进命令行、文档、JSON 夹具或日志。

安装验收在另一个干净虚拟环境执行，不依赖 editable 安装。
构建 wheel 后离线安装其已锁定依赖和 wheel，再从任意目录调用模块。
不得依赖旧仓库、当前 CWD 或个人 HOME 下的脚本完成最终验收。

### 10.3 新人可用性验收

本节是新增的产品准入条件，尚未开展真人实测。
下面数量是拟定门槛，不是已经达到的使用效果。

#### 参与者与准备

至少邀请 5 名未参与开发、未阅读内部实现规格的使用者。
记录其 QA 和终端经验，以说明样本范围。
管理员提前完成安装、锁定依赖和隔离实验资源准备。
参与者只使用一页指南、默认帮助和每项任务的合成业务说明。
不要求先读两份长设计文档，也不提供口头操作培训。

观察员只记录，不代输入命令或代处理问题。
参与者求助时如实计数；为安全而中止时保留失败原因。
不能把误操作记录和失败参与者从统计中删除。

#### 五项任务

| 任务 | 初始条件 | 独立完成的标准 |
|---|---|---|
| N1 首次实验 | 软件已安装，无真实网络和凭证 | 通过 demo 开始，知道结果仅适用于实验 |
| N2 开始需求 | 一份合成需求与有效 lab 项目 | 提供来源及必要业务名称，看到正确任务与环境 |
| N3 处理确认 | 有依据的问题和角色说明 | 理解影响范围并答复；需别人批准的仍保持待处理 |
| N4 错误恢复 | 一项明确可修复的数据准备错误 | 按提示改业务输入并继续，不查源码或手改 JSON |
| N5 续做和交付 | 已提交操作但响应中断，后续未完成 | 恢复正确任务，不重复副作用，导出可打开报告 |

实验修复使用已打包的合成构建，不要求新人修改程序。
普通任务只读/本地导出与远端写入应能从提示中区分。
既有有效答复不应在续做时重新询问。

#### 必须记录的观察项

- 参与者代号、背景、任务、开始与结束时刻。
- 是否独立完成，求助次数和具体原因。
- 是否正确理解实验/真实环境、待确认/已批准、失败/未知。
- 恢复是否成功，已有资料和答复是否被重复索取。
- 是否需要手改 JSON、源码或输入内部 ID。
- 是否发生越权操作、重复建单、重复上传或错误选择任务。

任务完成率按实际完成项数/全部规定项数计算。
恢复成功率按成功恢复次数/实际恢复任务次数计算。
分母为 0 时显示不适用，不能填写 100%。
逐项保存实际耗时，报告原始值、中位数和最大值。
尚无新人耗时基线，本轮不虚构分钟数或效率改善比例。

#### 拟定通过门槛

5 人各完成 5 项任务，共 25 项规定任务。
本轮要求 25 项均独立完成，不能靠平均值掩盖个别人的失败。
以下次数均要求为 0：

- 实现者代操作或提供内部知识才能完成的求助。
- 手改 JSON、源码或手填内部 ID 的日常任务。
- 越权或重复副作用。
- 同一有效版本与范围下的问题重复确认。

对确认范围、环境和最终结论的关键误解也判为不通过。
一般帮助阅读与展开详情属于正常操作，不计为实现者求助。
记录总操作次数，不预设缺乏依据的通用“最少几步”指标。

若有人失败，先修提示、入口或流程，再用新的未参与者复验。
原失败保留，不只重测已经熟悉流程的原参与者。
5 人样本只支持本轮任务和参与者范围的结论，不证明所有新人都能无障碍使用。

#### 自动化测试与真人验收的关系

自动化检查任务接口、选择、幂等、权限和输出一致性。
真人检查能否找到入口、理解原因、作出业务决定并安全恢复。
两者都需完成，不能以开发者演示或 pytest 通过替代新人观察。
JSON 中的 `usability` 场景为真人验证规格，不得由桩程序自动生成“真人通过”。

### 10.4 管理员与开发者的操作验收

管理员先预览配置，检查目标、连接器、权限与能力，再应用。
测试失败应保留原有效配置，展示具体待处理项。
测试人员复用配置，不再次申请或手填已核验资料。

开发者在 `api` 下验证底层命令，与日常任务入口比较同输入的业务结果。
高级入口不允许跳过证据、授权或副作用约束。
非交互调用缺少选择或决定时应立即返回明确阻断，而非等待输入。

## 12. 验收记录与最终判定

每轮生成独立 `verification_report.json` 和人读报告，至少包含：

- 实现提交、工作区是否干净、规则与本方案清单摘要。
- OS、Python、SQLite、执行器、模型与适配器能力。
- 每个 AC 场景的 pass/fail/blocked/not_applicable 及实际证据。
- 实际命令、退出码、JSON 回执、输入与输出摘要。
- 外部操作调用账本、平台对象和清理处置。
- 每项需求的实现状态、离线验收、真实接入和剩余限制。
- 新人任务原始记录、求助、恢复、关键理解与样本限制。
- 人工审阅人与身份核验方式；不得由 Agent 自行冒充。

测试不能只保存最后一份覆盖全部历史。
失败、重试、修复和新上下文结果都应可追溯。

最终交付分三次宣布：

1. **本地实现可验收**：适用的 offline/lab/parity/package 场景通过，规定新人任务验收也通过。
2. **指定测试平台可用**：真实空间、原生审批、模型等相关场景通过。
3. **指定部署生产只读验证通过**：仅对实际部署与窗口出结论。

全范围验收要求所有必需场景通过，必要人工审阅与新人实测完成，未验证项明确。
只完成自动化检查时，可以声明对应自动化范围通过，不能声明新人已好上手。
not_applicable 必须有适用性依据和有效决定；不能用于回避未实现能力。
若真实接入 blocked，只能宣布相应局部范围通过，不能宣称完全完成。

## 14. 与旧项目的比较规则

旧项目当前测试已通过，不意味着全部业务语义都正确。
等价比较只用于防止重构暗改已确认规则。

1. 保存旧校验器输出和完整输入，不在新测试运行时动态推导预期。
2. 比较门禁、分数、问题代码、指纹与追溯关系。
3. 对本地渲染固定配置、链接参数与输入，分别比较三种模式。
4. 对发现的旧缺陷保留差异，不要求新系统复制已确认错误。
5. 任何规则修正单独记录依据、确认人及受影响样本。
6. 同时验证原始材料、历史阶段文件与共享安装位置未改变。

不通过放宽规则、删除失败场景或减少范围来制造等价。
