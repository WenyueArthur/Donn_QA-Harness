# 新人可用性验收方案（真人实测脚本）

本文件对应测试与验收方案 §10.3，覆盖场景 AC-135、AC-138、AC-143、AC-144。

**状态：尚未开展真人实测。** 本文件是任务脚本与记录表，不是验收结果。
它不是 pytest 自动结果；pytest 中这四个场景记为 blocked。
任何程序、桩或开发者演示都不能代替本方案产生“真人通过”的结论。
没有实测记录时，产品只能显示“新人可用性尚未验证”。

## 1. 参与者与准备

### 1.1 参与者条件

- 邀请至少 5 名参与者。
- 参与者未参与本系统的开发。
- 参与者未阅读 `01-rebuild-design.md`、`02-validation-plan.md` 和源码。
- 记录每人的 QA 经历与终端使用经历，用于说明样本范围。
- 不要求参与者预先拥有飞书或缺陷平台的权限。

### 1.2 允许使用的材料

- 已安装产品的默认帮助，即 `python -m qa_flow --help` 的输出。
- 一页上手指南 `docs/qa-flow-rebuild/QUICKSTART.md`。
- 每项任务的合成业务说明，见本文件第 3 节的“发给参与者的说明”。

不提供口头培训，不提供两份长设计文档。

### 1.3 管理员准备步骤

每名参与者使用一套全新的目录。管理员在参与者到场前完成以下步骤：

1. 安装产品与锁定依赖，确认 `python -m qa_flow --help` 可以执行。
2. 断开真实网络，确认机器上没有模型、飞书或缺陷平台的凭证。
3. 为参与者建立空的工作目录，例如 `~/qa-trial/P1`，并在其中打开终端。
4. 把合成需求文件复制为工作目录下的 `需求.md`。文件来源是 `src/qa_flow/resources/lab/demo/refund-requirement.md`。
5. 按第 3 节各任务的“管理员预置”准备初始状态。
6. 启动屏幕录制或终端记录，记录内容只含合成数据。

### 1.4 观察员规则

- 观察员只记录，不代输入命令，不代处理问题，不作口头引导。
- 参与者求助时如实计数，并记录求助的具体原因。
- 为安全而中止任务时，记录为未完成，并保留失败原因。
- 误操作记录和失败的参与者不得从统计中删除。

以下情况不计为“实现者求助”：阅读帮助、阅读一页指南、使用 `--details` 展开详情。
以下情况计为“实现者求助”：需要实现者代操作，或需要实现者提供内部知识才能完成。

## 2. 观察记录表

每名参与者的每项任务填写一行。5 人各 5 项，共 25 行。重做同一任务时新增一行，原记录保留。

| 字段 | 填写内容 |
|---|---|
| `participant_pseudonym` | 参与者代号，例如 P1。不记录真实姓名 |
| `task_id` | N1 至 N5 |
| `started_at` | 开始时刻，ISO 8601 UTC，例如 `2026-11-16T01:00:00Z` |
| `finished_at` | 结束或中止时刻，格式同上 |
| `independently_completed` | 是否独立完成，`true` 或 `false` |
| `help_events` | 实现者求助次数，整数 |
| `resume_success` | 仅 N5 填写：恢复是否成功，`true` 或 `false`；其他任务填 `null` |
| `decision_understanding` | 对实验/真实环境、待确认/已批准、失败/未知的理解是否正确；填 `correct`，或写明具体误解 |
| `manual_json_or_source_edits` | 手改 JSON、源码或手填内部 ID 的次数，整数 |
| `unsafe_or_duplicate_effects` | 越权操作、重复建单、重复上传或选错任务的次数，整数 |
| `repeated_question_same_valid_scope` | 同一有效版本与范围的问题被重复询问的次数，整数 |
| `notes` | 求助原因、失败原因、中止原因和总操作次数 |

另外单独记录每名参与者的背景：QA 经历年限、终端使用经历。

记录文件为 JSON 数组，每个元素是上表的一行。示例：

```json
[
  {
    "participant_pseudonym": "P1",
    "task_id": "N1",
    "started_at": "2026-11-16T01:00:00Z",
    "finished_at": "2026-11-16T01:06:30Z",
    "independently_completed": true,
    "help_events": 0,
    "resume_success": null,
    "decision_understanding": "correct",
    "manual_json_or_source_edits": 0,
    "unsafe_or_duplicate_effects": 0,
    "repeated_question_same_valid_scope": 0,
    "notes": "共 4 次命令"
  }
]
```

## 3. 五项任务脚本

每项任务结束后，观察员向参与者提出“理解核对问题”，按回答填写 `decision_understanding`。
核对问题只在任务结束后提出，不在任务过程中提示。

### N1 首次离线实验（对应 AC-143）

管理员预置：空工作目录，无网络，无凭证。

发给参与者的说明：

> 你刚拿到这套 QA 工具。请按一页指南完成首次体验，并告诉观察员你看到的结果说明了什么。

独立完成的标准：

- 参与者自行执行 `demo` 并看到合成需求的当前状态与下一步。
- 参与者能指出结果只适用于合成实验。

理解核对问题：

1. 屏幕上的结果能不能说明真实业务或生产已经通过？正确回答为“不能”。

### N2 开始一个需求（对应 AC-143）

管理员预置：已有有效 lab 项目；工作目录下有 `需求.md`。

发给参与者的说明：

> 产品给了你一份需求文件 `需求.md`。请用这套工具开始这个需求，并说出系统为你建立的任务名称、来源和环境。

独立完成的标准：

- 参与者只提供来源，必要时提供业务名称。
- 参与者没有填写内部 ID、工作区路径或 JSON。
- 参与者说出的任务名称、来源和环境与屏幕一致。

理解核对问题：

1. 当前环境是实验还是真实测试环境？正确回答为“实验”。
2. 现在有几个需求任务？下一步操作会作用在哪一个？

### N3 处理业务确认（对应 AC-135、AC-143）

管理员预置：N1 的实验任务停在“有 1 项待本人确认、2 项需产品决定”的状态。

发给参与者的说明：

> 你是测试人员。技术方案已写明回调按 event_id 去重。请处理系统提出的待确认事项。
> 订单状态展示和通知归属由产品负责人决定，你没有得到产品的答复。

独立完成的标准：

- 参与者阅读了问题的原文依据与影响范围。
- 参与者只答复自己负责的问题。
- 需产品决定的问题保持待处理，或被转交；参与者没有代签。
- 参与者没有用“全部同意”一次处理多项。

理解核对问题（AC-135）：

1. 你刚才的答复算不算产品负责人的签字？正确回答为“不算”。
2. 还有哪些事项需要别人决定？由谁决定？为什么你不能决定？
3. 实验审批桩给出的模拟答复，是不是真人或已认证的批准？正确回答为“不是”。
4. 未取得原生平台批准的动作现在能不能执行？正确回答为“不能，仍受阻”。

### N4 从错误恢复（对应 AC-138、AC-143）

管理员预置：实验任务已完成设计类阶段，并预置一项可修复的合成数据准备错误。
预置方法由管理员在到场前完成，参与者不知道内部契约。

> 说明：截至本文件编写时，产品没有提供“预置可修复的数据准备错误”的公开入口。
> 开展 N4 之前，需要先由产品提供该入口，或由验收方确定一种只修改合成业务输入的预置方法。
> 在此之前 N4 无法执行，AC-138 保持 blocked。

发给参与者的说明：

> 继续这个需求时系统报告了问题。请只根据一页指南和屏幕提示处理，然后继续。

独立完成的标准：

- 参与者根据提示修正了被指出的业务输入，并使用“继续”。
- 参与者没有查源码、手改 JSON、手改数据库，也没有请实现者操作。
- 恢复后，恢复前已有的结果仍然保留。
- 修复之前，屏幕没有显示通过。

理解核对问题：

1. 出错时系统缺的是什么？已有哪些结果？
2. 修复之前，这个需求是通过、失败还是未判定？

### N5 中断续做与交付（对应 AC-143）

管理员预置：实验任务中一项外部动作已提交但响应中断，后续步骤尚未完成。
预置方法：在受控测试模式下让一次 `resume` 在发送后中断；该步骤由管理员完成。

发给参与者的说明：

> 你昨天做到一半，终端被关闭了。请继续这个需求，完成后把报告导出到 `./交付`，并打开报告确认内容。

独立完成的标准：

- 参与者恢复到正确的任务。
- 没有重复建单、重复上传或其他重复副作用。观察员在任务后查询实验平台桩核对数量。
- 参与者没有被重新索取已提供的资料或已生效的答复。
- 参与者导出了报告，并能打开返回的路径。

理解核对问题：

1. 导出报告有没有把内容写到飞书或缺陷平台？正确回答为“没有”。
2. 报告里哪些范围尚未验证？
3. 中断前那一步操作，系统是重新执行了一次，还是先核对了结果？

## 4. 计算方法与拟定门槛

以下数量是拟定门槛，不是已经达到的使用效果。

### 4.1 计算方法

- 任务完成率 = 实际独立完成项数 ÷ 全部规定项数。规定项数为参与者人数 × 5。
- 恢复成功率 = 成功恢复次数 ÷ 实际恢复任务次数。
- 分母为 0 时显示“不适用”，不填写 100%。
- 逐项保存实际耗时，报告原始值、中位数和最大值。
- 目前没有新人耗时基线，本轮不给出分钟数目标，也不给出效率改善比例。
- 记录总操作次数，不预设“最少几步”的指标。

### 4.2 通过门槛

本轮通过必须同时满足以下条件：

- 参与者不少于 5 人。
- 每名参与者的 5 项任务均独立完成，共 25 项。不用平均值掩盖个别人的失败。
- 实现者求助次数为 0。
- 手改 JSON、源码或手填内部 ID 的次数为 0。
- 越权或重复副作用的次数为 0。
- 同一有效版本与范围的问题重复确认次数为 0。
- 没有对确认范围、环境或最终结论的关键误解。把实验通过理解为生产通过属于关键误解。

平均耗时低不能抵消上述任何一项。

### 4.3 结论的适用范围

5 人样本只支持本轮任务与本轮参与者范围内的结论。
它不证明所有新人都能无障碍使用。

## 5. 失败后的处理（对应 AC-144）

1. 冻结本轮观察记录文件，记录文件的 SHA-256 摘要。
2. 评审失败、求助与误解的原因。原失败记录保留，本轮判定为不通过。
3. 先修改提示、入口或流程。
4. 邀请新的未参与者复验，不只重测已经熟悉流程的原参与者。
5. 复验结果与原记录分开保存，两轮都进入验收记录。

禁止以下做法：

- 只更换统计分母。
- 删除失败的参与者或失败的记录。
- 降低第 4.2 节的门槛，或降低原有的可靠性门禁。

## 6. 人工验收步骤

1. 确认第 1.3 节的准备步骤全部完成。
2. 逐人执行 N1 至 N5，观察员按第 2 节填写记录。
3. 每项任务结束后提出理解核对问题，填写 `decision_understanding`。
4. 每人结束后，查询实验平台桩，核对没有重复建单或重复上传。
5. 把 25 行记录保存为 `observations.json`，并计算其 SHA-256 摘要。
6. 执行 `python -m qa_flow api usability evaluate --input observations.json`，保存输出。
7. 由观察员按第 4 节人工复核该输出。人工结论与程序输出不一致时，以第 4 节为准，并记录差异。
8. 在验收记录中分别填写 AC-135、AC-138、AC-143、AC-144 的结论、参与者范围、记录文件摘要和观察员。

> 说明：自动化检查发现，`api usability evaluate` 当前的判定与第 4.2 节存在差异。
> 差异包括：参与者超过 5 人时个别人的失败可能被完成总数掩盖；同一任务的原失败记录在重做成功后不影响判定；
> `decision_understanding` 中的关键误解不参与判定。
> 因此第 7 步的人工复核不能省略。详见 `tests/acceptance/test_review_and_guidance.py` 中标记为 AC-143、AC-144 的计算规则检查。

## 7. 自动化测试与真人验收的关系

- 自动化测试检查任务接口、选择、幂等、权限和输出一致性。对应文件为 `tests/acceptance/test_task_frontend.py` 与 `tests/acceptance/test_review_and_guidance.py`。
- 真人验收检查参与者能否找到入口、理解原因、作出业务决定并安全恢复。
- 两者都需要完成。pytest 通过或开发者演示不能替代新人观察。
- AC-135、AC-138、AC-143、AC-144 的结论只能来自本方案的真人实测记录。
